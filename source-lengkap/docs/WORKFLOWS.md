# KSPPS website and connected portal concept

The approved public website is authored in `frontend-user/`, `frontend-petugas/`, `frontend-avalist/` and `shared/`; logos are in `public/assets/` and `dist/` is generated by Vite. The portals share a Worker API, a `DB` D1 binding and a private `BUCKET` R2 binding. This GitHub export retains binding names in `.openai/hosting.json` and deliberately excludes the original Site project identity.

Handoff baseline: v39, 14 October 2026. Read `../../panduan-codex/README.md` for project context and the distinction between application hosting and static Pages.

## Bantuan dan pelacakan keluhan, 27 Oktober 2026

Anggota mengirim **Subjek keluhan** (5–160 karakter) dan **Uraian keluhan** (10–4000 karakter) dari **Bantuan**. Server memberi nomor `KLH-<tahun WITA>-<urutan global minimal enam digit>` dan waktu masuk. ID kiriman dari browser hanya untuk mencegah duplikasi: pengulangan ID, pemilik dan isi yang sama tidak menambah nomor atau riwayat baru. ID akun sesi tetap menjadi pemilik kasus meskipun keanggotaan belum disetujui, sudah ditutup, atau kemudian berganti ruang keanggotaan.

Admin/Manajer membuka **Keluhan Anggota**, menetapkan PIC dan batas waktu masa depan per kasus. PIC Admin sesuai divisi Administrasi, Finance sesuai Keuangan, dan Manajer sesuai Manajemen. Perubahan penugasan/tenggat wajib beralasan. Finance hanya dapat membaca serta menindaklanjuti kasus yang ditugaskan kepadanya; Avalist ditolak. Endpoint keluhan menolak URL, query dan header pemilih anggota agar tidak mengubah identitas pelapor.

Status dimulai **Baru**. Setelah PIC dan tenggat tersedia, PIC/Admin/Manajer memakai **Mulai penanganan** ke **Dalam penanganan**. Tanggapan petugas dapat mempertahankan Dalam penanganan atau memilih **Menunggu tanggapan anggota**. Balasan anggota pada Menunggu tanggapan anggota atau **Selesai** mengembalikan kasus ke Dalam penanganan. PIC/Admin/Manajer juga dapat membuka kembali Selesai lewat tanggapan dengan pilihan status Dalam penanganan atau Menunggu tanggapan anggota sebelum penutupan. Penyelesaian wajib mencatat hasil 10–4000 karakter. Admin/Manajer memakai **Tutup kasus** hanya sesudah Selesai mempunyai hasil. Kasus **Ditutup** tidak dapat diubah atau dibalas. Hasil lama tetap ada pada riwayat ketika ada tindak lanjut sebelum kasus ditutup; penyelesaian berikutnya membutuhkan hasil baru.

API: `GET/POST /api/workflow/complaints`; `?view=staff` memilih antrean petugas; `GET /api/workflow/complaints/:id` memberi detail, riwayat dan izin tindakan. Mutasi `POST /:id/assign`, `/:id/reply`, dan `/:id/status` wajib membawa versi terkini. Mutasi kasus serta peristiwa riwayat berada dalam satu batch D1 dengan versi dan token bersyarat; penolakan versi atau kegagalan penulisan riwayat tidak meninggalkan perubahan setengah jalan. Tidak ada API edit/hapus riwayat atau penghapusan kasus. Penanda melewati batas waktu hanya berlaku pada Baru, Dalam penanganan dan Menunggu tanggapan anggota.

Izin detail `canReplyAsStaff` membedakan tanggapan petugas dari tanggapan pemilik. Pemilik yang juga PIC dapat memilih status petugas selama haknya masih aktif; kepemilikan saja tidak memberikan izin itu. Balasan pemilik tanpa pilihan status mengikuti aturan tanggapan anggota.

Migrasi tambahan: `0015_complaint_tracking.sql`, setelah seluruh migrasi terdahulu. Tes `tests/complaints.mjs` mencakup nomor lintas tahun WITA, pengiriman bersamaan, akses akun/PIC, divisi/tenggat, status/hasil wajib, kasus ditutup dan rollback. `tests/complaints-ui.mjs` memeriksa interaksi antarmuka. Fitur source ini tetap tidak mengirim atau menyimpan keluhan pada GitHub Pages. Hosting operasional dan penyedia sesi ditunda pengguna; aktivasi backend adalah tahap terpisah.

## Current workflow

1. Members register at `anggota.html#daftar` with identity/KTP, account, signature and initial savings proof.
2. Assigned Finance staff reconcile the payment. A one-page membership letter then becomes available in the member's Documents and Profile pages. Admin separately checks identity/KTP and approves registration before service access.
3. Members with active savings apply to a Manager offer within its remaining quota. Finance reconciles new money before Admin approves and generates the original-layout contract PDF.
4. Admin downloads that PDF, obtains the cooperative signature externally, and uploads the complete PDF. Members see the archived document.
5. From H-30, member notifications ask for an immutable choice: extend the same principal to another open project, or return principal on H. The reminder persists until confirmed, including after H.
6. Extension reserves the new project's quota atomically and creates an Admin draft linked to the original reconciled principal; no second transfer proof or reconciliation is required. Effective nisbah starts on the old end date, or the confirmation date if late, with no +10-day wait. The existing 31-to-1 adjustment and +365-day term remain.
7. A return creates a scheduled Finance task. Before H it cannot be started or recorded as paid; on H the original contract's displayed status becomes Selesai. Finance must actually transfer funds and record date, exact amount, reference and JPG/PNG/PDF proof. A conditional write prevents duplicate payment records. This is not an automatic bank transfer.
8. Manager **Akad Jatuh Tempo** reports ending principal, extensions, returns and undecided amounts, contract counts and distinct-member counts, filtered by contract end date. **Pekerjaan & Waktu Kerja** remains Manager-only.

Admin and Finance receive cooperative-wide queues without a name search or member selector. Each row retains its member reference for authorized review/file operations. Members can only submit decisions for their own contracts. Manager can open all three staff views; Admin and Finance retain their assigned role.

Document labels: `SPK <PROJECT> / <LETTER SERIAL ONLY> a.n <MEMBER NAME>` and `SPA <MEMBER NUMBER> a.n <MEMBER NAME>.pdf`. Download filenames replace `/` with `-` for filesystem compatibility. Internal automatic contract numbers and the original contract body/layout are unchanged. The membership letter preserves the supplied DOCX letterhead, wording and chair signature, with adaptive body sizing to stay on one page. Its effective membership date is the Finance reconciliation date in WITA. Refreshes do not consume another letter serial.

No seeded member or financial records are inserted by this release. Notifications are in-portal and refresh while idle; open forms are preserved. No email, WhatsApp, bank transfer or certified electronic-signature integration is configured. Financing applications retain their existing simulated implementation.

## Automatic member numbers

Each persisted registration receives `SKI-<registration year>-<serial>`, e.g. `SKI-2026-0001`. The year follows the original server-recorded registration timestamp in Asia/Makassar (UTC+8). The globally increasing serial is allocated by D1 and continues across years; it is padded to at least four digits and never truncated. The database enforces one allocation per profile and a unique member number. Editing, approval, repeat submissions and page refreshes keep the same number. Internal UUIDs remain separate references for requests and attachments.

Existing unnumbered registrations are assigned transactionally in original registration order when first read. The same number is displayed in both portals and new application snapshots. Historical snapshots and PDFs remain immutable; old request lists resolve their display number from the linked profile.

## Automatic contract rules

- Number: zero-padded serial followed by `/` and the code, e.g. `0001/SPK-SKI-MRBH-9/IX/2026`.
- Code: `SPK-SKI-MRBH-` + numeric agreement month + `/` + Roman agreement month + `/` + agreement year.
- New-money effective nisbah date: agreement date **+10 calendar days**; if the result is the 31st, advance it to the 1st of the following month.
- End date: adjusted effective nisbah date **+365 calendar days**, including leap-year arithmetic; this is not a calendar-year increment.
- The server computes every derived value. Posted manual serial/code/effective/end values cannot override these rules.
- `contract_numbers` reserves an atomic global serial for each request. Repeated/concurrent attempts for the same request retain the same number; distinct requests receive distinct numbers. Numbers continue across months/years. A failed generation may reserve a number for that request; it is never reassigned.
- The original generated file is immutable. A retry returns it, including after final upload.

## Original template and signature

`backend/templates/akad-penyertaan-modal.docx` is the supplied `Template Akad Digital Investor SKI(1).docx`. `contract-source.pdf` is its original two-page rendering. `backend/scripts/prepare-contract-template.py` uses PyMuPDF to remove only variable text regions and writes `contract-original-layout.pdf` plus `contract-layout.json`. `contract.json` retains the extracted source text and placeholder mapping.

The runtime fills the original pages, preserving both columns, all fixed clauses, header, footer, page count and signature positions. It does not reflow or redesign the document. Only variable text areas change. Font size adapts within those fixed areas; registration rejects values too long for the available space before approval. Text is never silently truncated.

The registered member signature is cropped to visible ink and fitted proportionally inside a **100 × 35 point** box in the original first-party signature area. The chair's area remains blank. No new concept banner is drawn over the source document; the concept notice stays on the website and in PDF metadata.

The uploaded final PDF is structurally checked and stored byte-for-byte with a SHA-256 hash. Uploading the unchanged initial PDF is rejected, and an existing final PDF cannot be overwritten. Completeness of both signatures is confirmed manually by the officer; it is not cryptographically verified. No Privy, e-meterai or certified signing service is connected. Fixed terms and second-party details are copied from the supplied template; the implementation does not reassess them.

## Previous demo reset

The owner explicitly requested deletion of all previous demo data. `backend/src/reset-demo.js` performs one idempotent release reset on the first request after deployment. It removes historical profile/request rows and old objects under the five workflow attachment prefixes. Its fixed cutoff is `2026-09-21T05:53:39.000Z`. New records and files at/after the cutoff are protected. A database completion marker prevents subsequent resets. If cleanup fails, it retries without marking completion. This is release maintenance, not a public reset endpoint. Schema migrations contain only schema changes.

## Other connected workflow

Member **Pengunduran Diri** now follows Admin → Finance → Manager. An active/overdue financing contract or an unfinished capital contract/application blocks submission and approval. Ended capital must also have its recorded extension or completed return, so closure cannot strand outstanding capital or an unconfirmed maturity choice. Admin may reject with a visible reason or approve; approval creates a Finance task for exactly Rp100,000 principal savings. Finance records the completed transfer, date, reference and mandatory JPG/PNG/PDF proof; only then does the request enter Manager's final queue. Final approval permanently closes that membership. The app records transfers; it does not initiate bank transfers. All three stages retain server-side audit timestamps and real actor IDs. Version checks, unique open requests and transactional guards prevent duplicate refunds or concurrent creation of a new contract during resignation.

The closed membership number and its records remain an archive. **Daftar ulang sebagai anggota** points the same authenticated identity to a fresh membership workspace. The former member supplies all registration data/files and initial savings again, even when their details are unchanged; the system allocates a new never-reused number. Old balances, documents, credits, tasks and financing are not reassigned. Closing a cooperative membership does not delete the user's login account. Admin can view the closed archive through the scoped member endpoints.

Admin's **Kontrak Pembiayaan** register records already-agreed financing contracts and their verified settlement. An overdue date alone does not release the resignation block. Members see their registered contracts. Financing applications, pricing, installments and payment execution remain the prior concept; this registry is not a full loan-origination or banking integration. Existing two-step resignation approvals are returned for Admin review under the new three-stage flow, with a new auditable task; no refund or account closure is fabricated.

Run `npm run test:withdrawal` for contract blocks, role/stage guards, rejection and cancellation, concurrent one-time refund, final closure, same-data re-registration, financial history isolation, archive access and audit tests.

## Authentication and production boundary

The previous platform sign-in/out integration and identity headers were removed on 26 October 2026. Private API access requires a verified session from the trusted server binding `AUTH`; missing credentials, a missing provider or an invalid session never authenticate a visitor. The verifier receives only session cookies or Authorization, and supplies a stable ID plus a verified email when available. It does not issue sessions or implement email/password login. Assigned accounts in `staff_accounts` authorize Admin, Finance and Manager operations; choosing a role in the UI does not grant it. Manager bootstrap is protected by an expiring server-side activation token, after which the Manager grants/revokes staff requests. Anonymous visitors only see public pages and portal shells. All private uploads require an authenticated owner or the appropriate assigned staff role. Finance does not receive member KTP/signature/contract content for other members.

The Site records reconciliations and payment confirmations but never moves money. Operational deployment still requires the cooperative's identity, banking, retention and signing arrangements.

## Admin / Finance and daily profit-sharing

The staff portal offers Admin and Finance entries and a role selector. Existing Admin layouts remain intact. Finance has a summary, a reconciliation queue, and a daily profit-sharing page. No live demo records were inserted by this release.

### Full capital offers

Full offers remain in the member portal for exactly 72 hours after fulfillment. The member API filters expired offers, while the manager retains every offer. No offer, application, or contract is deleted. A page already open removes an expired card without closing an active form.

`capital_offers.fulfilled_at` is recorded atomically by reservation triggers, including renewals. Document updates and same-amount corrections preserve it. Releasing capacity clears it; filling the quota again starts a new 72-hour period. Migration 0012 adds the nullable timestamp, reservation index and triggers. For previously full offers, the timestamp is reconstructed once from the latest recorded active submission/revision; older revisions do not retain amount history, so that legacy timestamp is an estimate. New reservations record the exact transition time.

`backend/src/finance.js` owns the server-side role context, reconciliation state and calculations. `staff_workspaces` persists the selected concept role; `finance_reconciliations` stores the proof identity, expected/received amount, bank reference/date, Finance decision, timestamp, actor and optimistic version. Each receipt retains member ownership; assigned Finance staff view the cooperative-wide queue. Manager can switch views; other staff cannot elevate their assigned role.

Finance reconciliation is required for Admin registration approval, capital-request approval, and new PDF generation. Finance cannot approve members, approve capital requests, generate contracts or upload the chair-signed PDF. Admin cannot submit Finance reconciliation or fetch the Finance payout endpoint. A previously generated PDF remains available for idempotent download. Replaced proofs or changed expected amounts invalidate an older reconciliation. Requests without a matching reconciliation, including legacy generated contracts, are excluded from the payment preparation list until Finance reconciles them.

The initial registration includes fixed principal savings Rp100,000 and mandatory savings Rp10,000/month (monthly or annual prepayment), plus the retained other savings/admin-fee fields. Additional mandatory savings now create persistent Finance reconciliation tasks. Financing applications remain simulated; their UI checks server-side savings eligibility at opening and submission.

Profit-sharing rules used in this release:

- Basis: **effective nisbah date**, with the first payment one calendar month later.
- For payment date **5 September 2026**, match effective dates **5 September 2025** through **5 August 2026**, one monthly cohort each. A contract effective 5 September 2026 is not due that day.
- Include capital contracts already generated or fully signed, with matching approved reconciliation. The detail view identifies a generated contract awaiting the cooperative signature. This follows the requested scope of contracts already made.
- Payments occur in monthly periods 1–12 and never after the stored end date (effective date +365 days). For a monthly date 29/30 absent in February, use the last day of that month. The source effective date remains unchanged.
- Amount per contract = principal ×5%, rounded half up to whole rupiah using integer arithmetic. Group by member identity and bank account, then total the rounded contract amounts. Distinct accounts for the same member remain separate transfer rows.
- Default date uses Asia/Makassar (UTC+8). It follows the day change while the page is open, unless the user selects a historical/future date. An open dialog is not interrupted.
- Show bank, account number, account holder, contract count, per-contract detail and overall total. Semicolon-delimited CSV preserves account text and neutralizes spreadsheet formulas. This is a preparation report, not a bank-upload format or proof of payment.
- There is no bank connection, money transfer, automatic email, or paid-status claim.

`npm run test:finance` covers the exact 12-cohort example, aggregation, 5% integer rounding, cutoff and expiry dates, short months and Makassar midnight. The existing contract lifecycle tests now perform Finance reconciliation before successful Admin approvals and test wrong-role and cross-account access.

## Staff timestamps and KPI reference

Only Manager has **Pekerjaan & Waktu Kerja**, with role/status/date filters, per-role averages, detailed WITA timestamps and a filtered CSV export. Admin and Finance dialogs have **Mulai mengerjakan** without showing KPI timestamps. Forms require that explicit start in the current UI, without clearing entered fields or selected attachments.

`backend/src/activity.js` stores append-only `staff_activity` events. Submission creates Admin review and Finance reconciliation tasks at the server's submission time. Withdrawal creates an Admin task. Admin approval queues PDF generation; successful PDF creation queues signed-document upload. Each successful save completes only that stage. Returning a request finishes that review round; an actual resubmission closes obsolete open tasks and creates a new round. Cancelled/superseded tasks stay visible and are excluded from averages. Repeated start clicks preserve the first start, even across concurrent requests. The authenticated account ID and role are recorded server-side; client-supplied actors/timestamps are ignored.

Business mutations and their activity event commit in a single D1 batch. The event insert checks SQLite `changes()` from the preceding guarded business write: rejected validation, wrong-role requests, failed version checks, duplicate submissions and failed PDF generation do not report completion. An event insertion failure rolls back the business change. There is no history-edit endpoint.

Daily payout preparation has a separate task, **Selesaikan persiapan**, and explicit confirmation of account/amount checks. This never marks a bank transfer paid. Its arrival is due-date midnight in Asia/Makassar, or later when the last required contract/reconciliation became available. Due dates since tracking began are materialized from the contract schedule when the report is requested, so unopened past days remain queued. Future dates are previews only. A changed transfer list receives a new task; earlier completed preparations remain in history. No scheduler or bank connection is claimed.

Response = first start minus arrival; processing = completion minus first start. These are **elapsed calendar durations**, including external waits, not measured active working time, working hours, or SLA scores. Report date filters include arrivals, starts, completions and ongoing work; completion counts are stage counts, not distinct members. Averages display their sample count and use complete timestamp pairs only. Older clients may save without a start: completion is retained but processing duration stays unknown, never an invented zero. Existing open records are baselined once; unknown prior stage arrival/start times stay blank.

The Manager report aggregates separately assigned staff accounts and records the authenticated actor on each action. Return tasks become actionable on H; late member choices are timed from their confirmation instead of inventing an earlier arrival.

- Existing workflow tests additionally verify the tracked registration, Finance, review, generation and final-upload stages. Portal tests verify both-role navigation, populated/empty KPI states, WITA formatting and the retained form behavior.

## Required member KTP photo

Registration now requires a JPG/JPEG or PNG KTP photo (maximum 10 MB) in the identity step and includes it in the final review. The selected image remains available while moving between steps. Its object URL is revoked when replaced or removed. The profile and Admin registration review show the signature on the left and KTP on the right; small screens stack them in that order. Clicking the KTP opens the original image through the authenticated profile endpoint.

The server independently requires `ktp` on new/revised profile submissions and validates extension, MIME, content and image structure before saving it to R2. PNG decoding is bounded to 8 megapixels; JPG metadata is bounded to 50 megapixels. It stores the original image, filename and content type, never a public asset URL. `GET /api/workflow/profile/ktp` is owner-scoped and returns a private, noncached image; no browser storage is used for persistence.

Admin registration approval requires an uploaded KTP and an explicit KTP inspection checkbox, in addition to existing identity/signature checks and Finance reconciliation. Approval records the server timestamp and authenticated reviewer ID in `member_profiles`. This is manual inspection, with no OCR or government identity-verification claim. Corrected registration clears the previous KTP verification. Its editor reloads the existing KTP, signature and payment proof; the member replaces only the files that need correction, and the submitted files are validated again. Contract PDFs and their signature layout do not change.

Legacy profiles display a clear missing-photo state. **Lengkapi foto KTP** allows an existing pending/approved profile to add its missing KTP using an optimistic version check. It preserves the existing savings proof, signature, member number, contracts and Finance reconciliation, and puts registration back into Admin's pending review with a new work-timestamp stage. A stored photo cannot be replaced through that endpoint; replacements follow an Admin-requested registration correction. No existing records are deleted or automatically marked KTP-verified.

## Member corrections and mandatory savings

Requests returned by either Admin or Finance expose their notes and **Perbaiki** actions on the member summary, profile and related request cards. A Finance return alone is sufficient to reopen registration, capital or mandatory-savings correction; no extra Admin return is required. Revisions use the existing request/member number with optimistic versions, preserve prior proof objects and restart the required KPI stages. Existing KTP/signature/proof are restored into the registration editor. Reusing an identical previously reconciled registration proof retains its Finance decision. Credited registration amounts cannot be changed through correction.

- Principal savings: Rp100,000, once on registration. Mandatory savings: Rp10,000/month or Rp120,000/year. Server validation owns these values; subsequent deposits contain mandatory savings only and require JPG/PNG/PDF proof (10 MB maximum).
- The new `savings_credits` table stores immutable verified receipts, uniquely keyed by owner/source kind/source ID. Finance approval, receipt insertion and the work audit commit together. Existing matching approved receipts are imported lazily and idempotently; no previous data is reset. Unverified or returned proof does not add available credit.
- Monthly allocation is derived server-side from the original registration date in Asia/Makassar, starting with the registration month. A date absent in a short month uses the last day, and the following month returns to the original anniversary day. It catches up on missed months without scheduled jobs or duplicate debits. Each response contains dated monthly obligations, allocated amounts, arrears and remaining prepaid balance. Total money deposited remains recorded as member savings.
- Active savings require an approved registration, principal at least Rp100,000, and all obligations due through today covered. A zero prepaid balance still covers the already paid current month; access becomes inactive when the next obligation is unpaid. Top-ups cover earlier unpaid obligations first. No grace period or late charge is added.
- Capital and financing screens are gated when savings are inactive; the capital API independently rechecks eligibility. Existing correction actions, savings replenishment, profile, documents and withdrawal remain reachable. Financing applications remain a simulation; the Admin contract/settlement register is persistent and controls resignation eligibility.
- Remaining prepaid credit at or below Rp30,000 produces an in-portal reminder with a deposit action, both on the summary and in notifications. This includes an account that skips directly below the threshold. Idle visible member pages refresh every minute; open forms, attachments, registration steps and focused inputs are not interrupted. There is no email/WhatsApp/push delivery or scheduler claim.
- Additional mandatory-savings deposits are reconciled by Finance; they do not require a second Admin savings approval. Source proofs, versions, Finance role, account ownership and received-amount matching remain server checked.

`npm run test:savings` verifies calendar coverage, the Rp30,000 threshold, overdue/inactive status, late replenishment, WITA and leap/short months. Workflow tests cover persistent receipts, both-role corrections, one-time principal, stale versions, credit idempotency and API eligibility. Portal checks cover reachable corrections, locked screens, prefilled revisions, reminder content and form retention.

## Avalist internal

`backend/src/avalist.js` owns the server rules; native Svelte pages live in
`frontend-petugas/src/components/avalist/` for operations. The independent personal portal
is `/avalist.html`, implemented in `frontend-avalist/`; shared read-only views live in
`shared/components/avalist/`. It has its own branded access screen and four-page navigation.
It calls only `/avalist/access` and `/avalist?view=personal`, and
never changes the selected staff role or loads operational queues. Entitlement is checked
server-side. Refresh/session failures remove stale personal data. Legacy `petugas.html#avalist-*`
links redirect to this entry, and staff role pickers link there instead of opening an
Avalist workspace inside the staff shell. There is no Avalist data in the member portal.
Manager registers an internal Avalist with only an email in Pengelolaan Avalist.
Name and bank details are optional at registration; complete bank details are required
before payment. Pending registrations can already receive assignments and complete old
proposals. No outbound invitation is sent. A trusted session service must verify the
registered email; `avalist-email.js` receives only that verified email and binds the grant
once to the stable account ID. Unverified email cannot claim access. Subsequent
authorization uses that ID, never a form-provided email. Email case is normalized without
provider-specific alias rewriting. Duplicate registrations and identity reassignment are
rejected. The email binding cannot be changed to transfer financial history.

`avalist_email_access` stores pending/bound grants separately from immutable assignment
and payment records. Pending people use a unique internal placeholder until first login;
there is no staff account until an authenticated claim succeeds. A conditional atomic
batch and per-claim token ensure only one identity wins concurrent claims. Existing
Admin/Finance/Manager permissions are preserved; otherwise only `avalist` is granted.
The claim creates an approved access-directory entry and audit event, allowing Manager
to revoke access normally. A bound grant never recreates revoked access. An inactive
pending profile cannot claim access; existing inactive recipients retain their own
history while their account access remains granted. Claims advance the financial
revision to prevent concurrent stale payment preparations.

Only Manager may register/edit recipients, assign recipients/rates, approve or reject
Admin proposals, and approve adjustments. Admin proposals have no financial effect
until approved. A proposal for all running contracts freezes its selected contract IDs
at submission; approval revalidates those contracts instead of silently including new ones.
Finance can prepare and record transfers, but cannot change assignments or percentages.

The member default is copied atomically by an INSERT trigger when a capital application
(including a renewal) is created. Changing it does not change earlier applications.
Existing legacy contracts start unassigned; Manager must explicitly set their avalist
and rate rather than silently attributing prior entitlements. Per-contract events apply
from the first scheduled due date on/after the chosen effective date. Identity and rate
are resolved independently by effective date and then event sequence. Events and paid
records are immutable. Earlier paid periods always use their original stored snapshot.

Regular payments use the existing Finance schedule and reconciled capital/renewal
funding. Per period: member 5%, avalist 1% or 2%, cooperative the remaining 4% or 3%.
Amounts round to whole rupiah; cooperative receives the rounding residual to preserve
exactly the rounded 10% total. The member's existing 5% calculation is unchanged.
Finance sees per-contract allocations and per-recipient totals. Preparing a payment
creates a versioned snapshot. Assignment/bank edits mark affected preparations for
review. Payment recording requires matching authoritative details, current version,
exact amount, transaction date/reference, proof, and explicit confirmation. Transfers
occur externally; this module records them and does not claim a bank integration or
that preparation of the member's payout is proof the member has been paid.

Manager-approved adjustments reference a completed regular payment and contain a
signed amount and reason. Positive amounts are additional transfers; negative amounts
record recoveries to the cooperative. A recipient transfer is represented by a recovery
from the former recipient and a separate payment to the new recipient. Original paid
records stay intact. Unique correction IDs prevent duplicate retry submissions.

A transaction revision guard covers assignment/recipient/payment operations and changes
to underlying contracts, reconciliation, maturity and staff access. A concurrent source
change aborts the entire D1 batch; uploaded proof is cleaned up on a rejected payment.
There is one regular payment per contract/due date. The append-only audit stores the
authenticated actor, reason and time. Migration 0013 contains bounded schema, indexes,
default inheritance, revision and immutability triggers; it does not backfill or reset data.

Personal views return only the recipient's own periods, minimal member name/number,
and their own paid history/proof. They do not return member KTP, bank accounts, contract
files or other recipient identities. Generic staff/member routes also deny the Avalist-only
account, so hiding navigation is not the authorization boundary.

`npm run test:avalist` checks API permissions, default inheritance, independent effective
periods/rates, residual allocation, private histories/proofs, source races, repeated payment,
immutable records, separate corrections/revocation, email-only registration, one-time identity
binding, duplicate/concurrent claims, preserved staff roles, and native form/navigation behavior.
The dedicated portal tests cover sign-in/out destinations, all four personal views, navigation,
revocation, session expiry, retries, and independent frontend bundles without staff APIs.

### Initial Avalist approval completeness

New proposals validate the presence of a recipient and rate against the history at the
selected effective date. The form names the unassigned contracts and requires explicit
initial values. Existing pending proposals expose missing fields to Manager for completion
in place. Completion applies only to absent fields on the affected contracts; it preserves
other contracts' existing independent rates and recipients. The original proposal payload
is retained, and the approving actor's additions are recorded in the decision and assignment
history. Admin/Finance cannot use this approval endpoint. No live assignment is inferred
or automatically approved during this update.

### Personal Avalist fee totals

The personal API returns `feeSummary` computed only from the signed-in recipient's
periods and payment ledger. `paid` is net completed regular payments and adjustments,
including archived contracts. `scheduledDue` is unpaid regular entitlement with due
date through today in Asia/Makassar; future periods are excluded. `pendingAdjustments`
is the signed total of approved, unpaid corrections due through today, including
those requiring bank review. `pending = scheduledDue + pendingAdjustments` and
`total = paid + pending`. Prepared regular transfers are not counted a second time.
Settling an adjustment moves its value from pending to paid without changing total.
A negative pending balance is displayed as a recovery due to the cooperative.
The personal summary shows the as-of date and explains the scope of Total fee diperoleh.

### Monthly personal fees

`monthlyFees` is scoped to the authenticated recipient before aggregation. Monthly
`total` follows each fee's due month and includes the whole month's assigned schedule,
including upcoming dates and approved positive/negative corrections. Paid regular
fees come from immutable ledger records; prepared regular transfers are excluded to
avoid duplicating schedule rows. Archived contract payments remain included.

Monthly `paid` is net cash based strictly on `transfer_date`, never the date Finance
recorded it (`paid_at`). A September entitlement settled in October belongs to September's
fee total and October's cash payment total. `paidForPeriod` groups completed payments
by their due month, so `pending = total - paidForPeriod`; monthly cash must never be
subtracted from the month's entitlement. `notDueYet` identifies upcoming unpaid regular
fees. A month/year picker defaults to the current Asia/Makassar month, preserves choices
on refresh/navigation, and shows zero for months without records. Lifetime totals remain
available in the expandable Akumulasi hingga hari ini section.

## Modular Svelte source refactor — 14 October 2026

The public URLs and API contracts are retained. Browser controllers assemble explicit feature modules. Each portal instance owns its services and state; cross-feature calls use explicit `app.services` dependencies, not window globals or global service registration. The old `shared/services` singleton registry was removed in v39. All dynamic views are native Svelte components/snippets; HTTP transport and state coordination are separate, and portal disposal releases listeners, timers and requests. The legacy global test-driver aliases exist only inside the JSDOM test bundle. Native Svelte cards/tables and smaller Avalist components retain the same controls and states. Backend routes and service implementations are grouped by feature; database migrations, template assets, and financial rules are unchanged. See PETA-KODE.md for ownership and troubleshooting paths.

One approved portal snapshot accepts Svelte CSSOM serialization of the contract progress width (`width: 65%;` instead of `width:65%`); the normalized element/content diff contains only that equivalent style attribute.
